У [першому дописі](/blog/qualityforge-qa-polygon) я пояснив, навіщо QA-інженеру власний полігон. Логічним наступним кроком здавалося взяти першу фічу й почати будувати продукт.

Ми зробили інакше: спочатку спробували побудувати середовище, у якому локальна LLM зможе працювати зі специфікаціями, кодом і тестами. Тобто першим експериментом QualityForge стала не Feature 001, а спроба налаштувати сам спосіб розробки.

На папері схема виглядала привабливо:

```text
local model -> coding agent -> specification workflow -> repository
```

На практиці між цими стрілками виявився окремий проєкт.

## Чому взагалі local-first

Ідея була не в тому, щоб будь-якою ціною уникнути хмарних моделей. Хотілося перевірити більш контрольований сценарій: модель працює локально через Ollama, агент взаємодіє з репозиторієм через OpenCode, а Spec Kit задає повторюваний шлях від вимоги до реалізації.

Такий підхід обіцяв кілька приємних властивостей: локальні дані, передбачуване середовище, контроль конфігурації й можливість повторити запуск без залежності від конкретної chat session. Специфікації при цьому залишалися звичайними файлами в git, а не домовленостями, похованими десь між двадцятьма повідомленнями.

Початкова гіпотеза була обережною: якщо вимоги, перевірки та правила роботи агента зберігати як версіоновані артефакти, ми зможемо оцінювати не лише згенерований код, а й сам процес розробки.

Це ще не було твердженням, що локальна модель краща. Це було питання: **чи вистачить її для керованого SDD-циклу?**

## Модель запускається — експеримент ще ні

Локальні тести йшли на MacBook Pro з M2 Max і 32 GB unified memory. Для звичайної розробки це солідна машина. Для великої моделі, IDE, браузера, Docker та довгого контексту одночасно — вже переговори за кожен гігабайт.

У репозиторії ми зафіксували два профілі через Ollama:

- `gemma4:12b-mlx` як швидший профіль для документації, fixtures, unit tests і невеликих змін;
- `gemma4:26b-mlx` як coding-профіль для feature implementation, debugging та integration work.

Для них обмежили context window до 16 384 і 32 768 токенів, одну задачу на ітерацію та максимум п’ять пов’язаних файлів. Ці правила добре показують реальність експерименту: контекст і ресурси вже були частиною дизайну процесу, а не невидимою деталлю інструмента.

У робочих нотатках фігурували й інші кандидати, але повного однакового benchmark для всіх моделей ми не зберегли. Тому тут не буде таблиці «хто переміг». Сам факт, що модель відповіла на prompt або відредагувала файл, нічого не доводив про її здатність стабільно пройти багатокроковий цикл: прочитати контракт, втримати scope, змінити код, виконати перевірки й чесно зупинитися перед human gate.

Був і дуже людський для LLM момент: під час одного аналізу модель раптом перейшла на Bengali. Я пам’ятаю цей епізод, але raw log не зберігся, тому це анекдот зі стенда, а не відтворений benchmark. Висновок із нього скромний: «запустилося» і «надійно виконує workflow» — різні статуси.

## Ollama була лише нижнім шаром

Ollama вирішувала inference: завантажити модель і дати їй згенерувати відповідь. Але для роботи з репозиторієм потрібен був агентний шар — читання файлів, зміни, запуск команд і передача контексту. Цю роль мав виконувати OpenCode.

Поверх нього ми спробували встановити Spec Kit. Його задача — не «написати код за нас», а зробити етапи видимими: constitution, specification, clarification, plan, tasks, implementation. У QualityForge constitution мала бути канонічним набором правил, а Feature 001 — першим контрактом, який пройде цей маршрут.

Ініціалізація Spec Kit справді додала OpenCode integration, `.specify/`, копію constitution і набір `speckit.*` command-файлів. Git це підтверджує. Але тут ми отримали перший важливий урок: **наявність command-файлу ще не означає, що команда реально доступна агенту**.

Потрібно було окремо перевіряти весь ланцюжок:

```text
command file -> discovery -> invocation -> context transfer -> actual agent behaviour
```

Кожна стрілка могла зламатися незалежно. OpenCode, запущений одним способом, не обов’язково був доступний як звичайна команда в shell. Службовий каталог міг не потрапити в git. Constitution могла опинитися у двох місцях, і тоді поставало просте, але неприємне питання: яка з них головна? Згенеровані slash commands виглядали переконливо, проте сам Markdown не створював магічний runtime dispatch.

Жодна з цих проблем окремо не була катастрофою. Разом вони означали, що ми дедалі більше тестуємо склейку інструментів, а не QualityForge.

## Що залишилося в git

Репозиторна історія добре показує порядок подій. Ще до ініціалізації Spec Kit у проєкті вже були `AGENTS.md`, constitution, local-model profiles і правила на кшталт «одна задача на ітерацію», «focused tests перед full suite» та «ніякого commit без human approval».

Наступний planning commit установив Spec Kit 1.0.6 з integration для OpenCode: додав `.specify/`, manifests, shell scripts, templates і `speckit.*` commands. Тобто це не була розмова про майбутній setup — артефакти справді з’явилися в історії.

Але git фіксує файли, не поведінку runtime. Він може підтвердити, що command існував, але не те, що конкретна session його знайшла, правильно передала context і виконала потрібну роль. Саме ця різниця між **installed artifact** і **observed execution** пізніше стане важливою, коли ми дійдемо до reusable Codex Skill.

## Коли setup став головним продуктом

Це був корисний момент для зупинки. Початкова мета — дослідити SDD і QA-процес на реальному продукті. Але в експеримент одночасно потрапили щонайменше чотири незалежні змінні:

- якість і розмір локальної моделі;
- обмеження пам’яті та context window;
- надійність агентного runtime;
- інтеграція Spec Kit із конкретним клієнтом.

Якби наступна задача провалилася, ми не знали б, що саме винне: слабка специфікація, помилка реалізації, втрата контексту моделлю чи command, який взагалі не був викликаний так, як ми думали.

Для експерименту це погана конструкція. Коли змінних забагато, кожне пояснення стає зручним і жодне — переконливим.

## Поворот до Codex/ChatGPT

Ми не довели, що локальні моделі непридатні для SDD. І не проводили контрольованого порівняння local model проти Codex за часом, вартістю чи якістю.

Так само ми не маємо повного архіву однакових runs для кожної моделі, точних timing measurements або стабільної статистики memory pressure. Тому рішення не було результатом benchmark leaderboard. Воно ґрунтувалося на спостереженні за системою в цілому: занадто багато роботи йшло на стабілізацію inference та integration, перш ніж ми взагалі доходили до перевірки SDD.

Рішення було прагматичнішим: для основного QualityForge-експерименту прибрати одну велику невизначеність. Реалізацію перенесли на Codex/ChatGPT, а local-first перестав бути обов’язковою умовою. Так ми могли досліджувати специфікації, review, тести, evidence та human decisions, не змішуючи це з окремим benchmark локального inference.

Важливо, що напрацьовані правила не зникли. У репозиторії залишилися constitution, requirement IDs, обмеження scope, одна задача на ітерацію, вимога запускати перевірки та заборона commit без human approval. Тобто ми змінили engine, але не відмовилися від контрольованого процесу.

## Що насправді дав перший невдалий маршрут

Local-first спроба не стала основним способом розробки QualityForge, але й не була марною.

Вона показала три речі.

По-перше, модель не можна оцінювати окремо від runtime та інструментів. Reasoning, tool use, command discovery і передача контексту разом утворюють систему.

По-друге, версіонований Markdown корисний як контракт, але не є доказом виконання. Наявність інструкції, command або пізніше навіть `SKILL.md` ще треба підтвердити реальним invocation.

По-третє, інфраструктура експерименту може непомітно стати самим експериментом. Іноді правильне інженерне рішення — не «дотиснути setup», а прибрати зайву змінну й повернутися до початкового питання.

Після цього ми нарешті перейшли до Feature 001 і побудували перший суворий цикл від специфікації до acceptance. Там уже з’явилися canonical spec, незалежний review, human gates і правило `no commit before approval`.

Але це наступна історія: **від специфікації до acceptance — наш перший SDD workflow**.
