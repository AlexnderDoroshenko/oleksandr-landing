У [першому дописі](/blog/qualityforge-qa-polygon) я описав QualityForge як полігон, де інженерна навичка має залишати перевірюваний доказ. Наступне питання було значно практичнішим: як побудувати сам полігон за допомогою LLM і при цьому не перетворити розробку на серію переконливих, але неперевірених відповідей у чаті?

Першим експериментом стала **Feature 001: Reproducible Platform Baseline**. Її завдання звучало скромно: підняти відтворюваний локальний baseline із backend, web UI, PostgreSQL і Redis. Але саме на цій базовій фічі ми вирішили перевірити навмисно суворий SDD workflow — процес, у якому реалізація рухається від погодженої специфікації та її acceptance criteria.

## Гіпотеза, а не релігія

Початкова гіпотеза була такою:

> Точна специфікація, автоматизовані тести, незалежний review та явне право людини ухвалювати рішення мають зробити LLM-assisted development більш контрольованою і спостережуваною.

Ключове слово тут — **мають**. Ми ще не знали, чи буде такий процес швидшим, дешевшим або зручнішим. І точно не намагалися довести, що існує єдиний «правильний SDD».

Нам був потрібен експериментальний baseline: достатньо суворий, щоб дефекти процесу не губилися у неформальних домовленостях. Якщо пізніше послаблювати правила, хотілося розуміти, що саме ми прибрали і який ризик повернули.

## Спочатку контракт

Канонічним джерелом істини для Feature 001 був не чат і не остання відповідь агента, а `specs/001-platform/spec.md`. У специфікації з’явилися стабільні requirement IDs: `PLAT-FR-001` для запуску середовища, `PLAT-FR-002` для readiness, `PLAT-FR-003` для correlation ID, `PLAT-FR-004` для детермінованого reset.

Це важлива різниця. Формулювання «зроби healthcheck» майже гарантовано породжує різні уявлення про готовність сервісу. Контракт уточнював, що liveness не дорівнює readiness, а not-ready response має показати стан компонентів без витоку секретів. Для correlation ID було зафіксовано, де саме він має збігатися: response header, structured log і OpenTelemetry span attribute.

Специфікація також казала, чого **не** робити. Kubernetes і cloud deployment були поза scope. Пізніше кожен task отримав ще точніші межі: UI не забирав собі Compose чи CI, CI не підміняв evidence publication, а cross-platform verification не ставав повторною повною acceptance-кампанією.

Feature 001 розклали на дев’ять обмежених tasks — від `PLAT-T01` із backend liveness до `PLAT-T09` із platform verification. Це давало кожному кроку власний контракт завершення й не дозволяло назвати всю feature готовою лише тому, що перший happy path уже працював.

Для LLM ці межі були не бюрократичною декорацією, а парканом навколо завдання. Модель може дуже старанно побудувати те, чого ніхто не замовляв. Чіткий out-of-scope економить не токени, а наслідки ентузіазму.

## Workflow зі стоп-кранами

Першу версію процесу ми будували за такою послідовністю:

```text
SPEC
  -> human review
  -> correction
  -> human approval
  -> implementation
  -> acceptance review
  -> human approval
  -> atomic commit
```

Перед implementation людина мала переглянути контракт і явно його схвалити. Якщо review знаходив неоднозначність, спочатку змінювалася canonical spec, а не приховано «уточнювалася» поведінка в коді.

Після implementation автоматичні перевірки ще не давали права оголосити task завершеним. Кандидат проходив acceptance review: окрему перевірку реалізації та evidence проти погодженого контракту. Лише після фінального human approval можна було змінити task status і створити атомарний commit.

Правило **no commit before approval** було свідомо жорстким. Commit тут означав не «збережуся про всяк випадок», а твердження: цей вертикальний slice пройшов погоджений цикл і має зрозумілу історію. У git log це видно як окремі кроки: backend liveness, readiness probes, correlation, database lifecycle, UI, Compose baseline, CI gates, evidence publication і platform verification.

Людина при цьому не перевіряла кожен рядок замість інструментів. Її роль була іншою: затвердити зміст контракту, прийняти або відхилити evidence, дозволити зміну статусу та commit. Агент міг пропонувати й виконувати, але не міг сам собі видати сертифікат якості.

## Від requirement до доказу

Ми хотіли бачити не тільки список тестів, а повний ланцюжок:

```text
requirement -> implementation -> tests -> evidence
```

Наприклад, `PLAT-FR-003` вимагав наскрізний correlation ID. Реалізація включала middleware, structured logging і tracing. Тести перевіряли генерацію нового ID, збереження валідного вхідного значення та присутність ID у потрібних точках. `docs/traceability.md` зв’язував requirement із task, конкретними перевірками та прийнятим статусом.

Для складніших platform-сценаріїв одного unit test було замало. Evidence мав зазначати середовище й commit, пов’язані requirement IDs, процедуру, спостереження, висновок, обмеження та cleanup. Так ми розділяли кілька різних речей:

- контракт у spec і plan;
- сирий результат виконання або CI log;
- curated evidence у репозиторії;
- traceability map, яка пояснює, що саме цей доказ підтверджує.

Це захищало від знайомого ефекту: «десь був зелений job, отже все готово». Зелений job доводить лише те, що в ньому справді запускалося і що його assertions уміли помітити.

## Чому Feature 001 була хорошим першим експериментом

Platform baseline здається простою інфраструктурною роботою, але в ній багато перевірюваних меж.

Чи залишається backend live, коли PostgreSQL недоступний? Чи readiness чесно називає проблемний компонент? Чи reset працює лише у дозволеному profile? Чи teardown видаляє тільки ресурси поточного checkout? Чи browser отримує нормалізований same-origin response, не бачачи внутрішню адресу backend? Чи bootstrap вкладається у deadline на описаному baseline, а не «швидко працює у мене»?

Ці питання дозволяли перевірити SDD не на абстрактному `hello world`, а на системі з runtime, даними, мережею, failure modes і різними типами доказів. Водночас scope ще залишався обмеженим: без production deployment, Kubernetes і бізнес-функцій майбутніх feature.

## Що ми хотіли вимірювати

У звичайній acceptance-перевірці основне питання звучить так: чи відповідає реалізація контракту? У цьому експерименті було друге питання: **що відбувається із самим способом розробки?**

Крім результату тестів, ми хотіли спостерігати:

- де виникають уточнення і чи змінюють вони канонічний контракт;
- скільки correction/review cycles потрібно кандидату та де потрібне рішення людини;
- які дефекти знаходять automated checks, а які — незалежний acceptance review;
- чи відновлюється зв’язок від requirement до коду, тесту й evidence;
- які перевірки справді виконані, а які результати повторно використані;
- які claims залишаються непідтвердженими через відсутній environment або артефакт.

Саме тому evidence фіксував не лише `PASS`, а й контекст, limitations та cleanup. Відсутня історична деталь мала залишатися відсутньою, а не магічно перетворюватися на успіх після чергового редагування Markdown.

Тут є важлива чесність: для Feature 001 не збереглася повна task-level статистика всіх циклів і human interventions у формі, яку можна коректно агрегувати. Тому ми не можемо постфактум заявити, що v1 скоротив роботу на певний відсоток. Але сам експеримент показав, які дані треба записувати надалі, щоб порівнювати процеси, а не враження від них.

## Навіщо було починати настільки суворо

Суворий workflow дав нам контрольну точку.

Канонічна специфікація зменшувала простір для тихої зміни вимог. Human gates залишали продуктові й ризикові рішення за людиною. Atomic commits робили історію task-level. Independent review відокремлював авторську впевненість від acceptance. Traceability та evidence показували не тільки результат, а шлях, яким ми до нього дійшли.

Це не доводить, що кожне завдання потребує однакової глибини review. Навпаки: без такого baseline було б важко відрізнити розумне спрощення від звичайної втрати контролю. Спочатку ми навмисно викрутили регулятори вправо, щоб побачити систему в роботі.

## Контроль теж має ціну

Feature 001 дійшла до реалізації, CI та acceptance evidence, але експеримент не закінчився красивою фразою «усі тести зелені». Далі з’ясувалося, що green automated tests ще не гарантують acceptance контракту, а незалежний review може знайти те, чого automation не перевіряла.

З іншого боку, повторні повні review, approval points і публікація evidence почали створювати помітний process overhead. Саме ці спостереження пізніше підштовхнули нас до risk-based SDD v2 — але це вже не історія цього допису.

Суворий workflow дав нам видимість і контроль. Та згодом ті самі механізми контролю стали частиною проблеми.

Наступний експериментальний звіт — **Green tests, broken contract**.
