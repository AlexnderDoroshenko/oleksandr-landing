Звичайний pet-проєкт часто показує лише фінальний код. Для QA-портфоліо цього недостатньо: важливо продемонструвати, як інженер аналізує вимоги, бачить ризики, проєктує перевірки, будує quality gates і пояснює результат команді. Так з’явилася ідея **QualityForge Lab** — керованого QA-полігона, де кожна навичка завершується перевірюваним доказом.

## Не ще один магазин із Playwright

Полігон задуманий як навчальна платформа керування замовленнями та доставкою. Домен достатньо знайомий, щоб не витрачати тижні на пояснення бізнесу, але в ньому є все необхідне для складних тестових сценаріїв: ролі, гроші, залишки, стани замовлення, асинхронні події та AI-асистент.

Ключові ролі — customer, merchant, courier, support та admin. Замовлення проходить state machine від `CREATED` до `DELIVERED`, але може бути скасоване, повернуте або опинитися в конфлікті через паралельні операції. Каталог додає валюти, промокоди, округлення та конкуренцію за останній товар.

Це створює реальні задачі для state-transition testing, boundary values, decision tables, API/UI automation, SQL, idempotency, retries та eventual consistency.

## Навичка має залишати доказ

Головний принцип полігона простий: недостатньо сказати «я знаю JMeter» або «працював із security testing». Для кожної навички потрібні:

- конкретний challenge;
- артефакт — код, звіт, dashboard, ADR або RCA;
- критерії проходження;
- рівень складності;
- коротка рефлексія про рішення та компроміси.

Наприклад, performance testing у такій моделі — це не скриншот із графіком. Це workload model, навантажувальний тест checkout API, виявлений bottleneck, підтвердження метриками й повторна перевірка після виправлення.

## Контрольовані дефекти замість випадкових багів

Окрема частина QualityForge — «музей дефектів». Проблеми вмикаються через feature flags: подвійна подія замовлення, повільний SQL-запит, застарілий cache, приймання простроченого JWT або витік персональних даних у лог.

Це дозволяє тренувати не лише знаходження дефекту, а повний цикл:

1. Виявити симптом.
2. Зібрати логи, метрики й traces.
3. Локалізувати причину.
4. Оцінити ризик і пріоритет.
5. Перевірити виправлення.
6. Зафіксувати RCA та regression coverage.

Такий підхід робить troubleshooting повторюваною вправою, а не везінням під час тестування.

## Від базового API до AI та security

MVP починається без зайвої складності: auth, catalog, order state machine, PostgreSQL, REST API, простий web UI, Docker Compose, API/UI tests, логи та кілька контрольованих дефектів.

Далі полігон розширюється асинхронними подіями, observability, performance і security-перевірками. AI/RAG assistant додає інший клас ризиків: prompt injection, доступ до чужих замовлень, застарілі документи, неправильні відмови та витік PII. Тут уже потрібні datasets і метрики — relevance, faithfulness, refusal correctness, latency та cost per request.

## Що має вийти

QualityForge Lab — це одночасно портфоліо, тренажер для співбесід і простір для інженерних експериментів. Його цінність не в кількості автотестів, а у traceability між ризиком, рішенням і доказом.

Наступний практичний крок — скласти Skill Coverage Map: `навичка → challenge → інструмент → артефакт → критерій проходження`. Саме ця карта перетворить великий список технологій на послідовний backlog розвитку QA-інженера.
